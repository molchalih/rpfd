# fixtures

The committed fixtures, and what they do and do not prove. A fixture is what one
archive of the test corpus looked like to an implementation that is not ours,
generated by `tools/oracle`; see `tools/oracle/README.md` for the semantics of
each field.

## The policy

No game data is tracked here, ever — DR-006, and `.gitignore` enforces it. A
fixture is a **description** of an archive: entry tables, sizes, flags and
checksums. Most are a few tens of kilobytes; the largest is 959 KB, for three
archives of 2,145 entry rows between them, of which 2,137 are files. All of
them are reviewable in a diff.

The archives themselves live outside the repository. Tests locate them through
`RPF_CORPUS`, a directory path. A fixture records the `sha256` of the archive it
was generated from, so a test can confirm it is looking at the same bytes rather
than at something that merely has the right name.

**With `RPF_CORPUS` unset, or the named archive absent, a test skips and says
what it skipped.** It does not fail, and — the part that matters — it does not
pass quietly. `cargo test` hides a passing test's output, so the message alone
is not enough: set **`RPF_REQUIRE_CORPUS=1`** and a skip becomes a failure. Use
it whenever the corpus is supposed to be present, so that "green" and "it ran"
are the same claim:

```
RPF_CORPUS=/path/to/corpus RPF_REQUIRE_CORPUS=1 cargo test --all
```

A green suite that tested nothing is the most expensive outcome available here,
so the skip is reported rather than swallowed.

**That flag asks for the whole corpus, not for the sample.** One fixture is
committed per unencrypted archive, and the gated leg rebuilds each one from the
archive its own `source.path` names, so a required run needs **all five of them
present** — the five in Provenance below. A missing archive is a skip, and
`RPF_REQUIRE_CORPUS=1` turns each skip into a failure naming the path it could
not open, which is the usual reason this command fails on a machine where the
sample alone is in place. The two exclusions described in the next section are
not among the five and are not asked for: an encrypted archive needs no fixture,
and neither does `cost_deflate/deflate.rpf`. Which five they are, and what each
one is, is the Provenance table below.

## What checks them, and what it does not

`crates/rpf-core/tests/oracle.rs` is the check, and it has two legs.

**Without a corpus** — which is continuous integration, always — every oracle
fixture is parsed into the document its generator emits and re-emitted. The
committed bytes must be exactly that: field order, ordering of `files[]`,
indentation, the field set each entry kind carries. It is a **schema and format
lint, not a check of any value**: a hand edit, a field nobody writes any more,
or a fixture produced by something other than `tools/oracle` fails here without
an archive in reach, and `tools/oracle` — which links the reference
implementation — is never compiled. A fixture whose `file_offset` reads
`999999` where the archive says `31232` round-trips perfectly and passes. Every
value in a fixture is checked by the corpus-gated leg below and by nothing else.

**With `RPF_CORPUS`** each fixture is rebuilt from the archive it names in
`source.path` and compared byte for byte, and every unencrypted archive under
the corpus root must have one, bar two exclusions. `generator` is the one block
carried across the rebuild rather than measured: it records which
implementation was read, which is provenance and not something an archive can
be asked for.

Both exclusions are deliberate, both are permanent rather than an outstanding
job, and the gated leg states each by name rather than passing over it. Its
closing line counts them: so many archives examined, so many encrypted and so
many built here, deliberately without a fixture.

**An encrypted archive has no fixture**: opening one unkeyed fails with the tag
in hand, so the test prints `NO ORACLE <path>: encrypted (tag …)` for each and
fails if one ever acquires a fixture. The generator wants a pre-dumped key blob
and DR-006 refuses to hold one.

**An archive this repository built itself has none either.** `oracle.rs` holds
those by exact relative path in `BUILT_HERE`, each with the reason beside it,
and for a match it asserts the archive has **no** fixture, prints
`NO ORACLE <path>: <why>` and moves on. There is one entry:
`cost_deflate/deflate.rpf`, written by `tools/cost/make-deflate-subject.sh` from
generated content. A fixture records what an archive looked like to an
implementation that is not ours, so a fixture for our own packer's output would
be circular — it would fire on any change to the packer rather than detecting
our reader drifting away from the reference, which is the only thing it is here
to catch. It would also pin a `sha256` for a subject that is rebuilt on demand,
making a file every gated run has to find. What it is for is stated by the
script that writes it: 53 large entries of generated text that deflate about
4.7:1, so that a rebuild has to re-compress rather than copy.

## Provenance

| Fixture | Archive | Verified against |
|---|---|---|
| `rmrp_bp16_meringls63amg24.json` | `rmrp_bp16_meringls63amg24/dlc.rpf`, a FiveM vehicle add-on, unencrypted | Independently walked in Python before this fixture existed. The two readings agree on every field of all 27 file entries and all 6 directory entries — zero disagreements |
| `rmrp_clothes.json` | `rmrp_clothes/dlc.rpf`, a community clothing pack, unencrypted | `rpf-core`, which rebuilds the whole document byte for byte — 3 archives, 2,145 entry rows, 2,135 leaf checksums. Weaker than the row above, and the difference is worth stating: the second reading here is our own reader rather than a third implementation, so what it establishes is that two implementations agree and not that both are right |
| `rmrp_vesta.json` | `rmrp_vesta/dlc.rpf`, a community vehicle pack, unencrypted | The same: `rpf-core` rebuilds it byte for byte. Its `sha256` and its byte count are also what `docs/corpus.md` recorded from a separate reading |
| `rmrp_vestacross.json` | `rmrp_vestacross/dlc.rpf`, a community vehicle pack, unencrypted | The same. `docs/corpus.md` took no `sha256` of this one, so the fixture is the first record of it |
| `rmrp_volgas.json` | `rmrp_volgas/dlc.rpf`, a community vehicle pack, unencrypted | The same, and its `sha256`, byte count and entry counts are `docs/corpus.md`'s, measured separately. This is the **second producer**: nine of its entries carry four bytes of zlib trailer after the deflate stream, which the fixture pins as extracted lengths |
| `rbf-metadata.json` | Every `RBF` payload in the 358 archives of both GTA V installs, extracted and classified by content | Not an oracle fixture. It is a **manifest**: a count, a byte total, the root-element and extension histograms, and one `sha256` per payload. `docs/metadata-encodings.md` is the independent reading — its root histogram was measured by a separate probe and agrees with this file's exactly |
| `pso-metadata.json` | Every `PSO` payload in the same 358 archives, likewise classified by content | The same kind of manifest, with one difference: it carries **one `sha256` of the sorted per-payload digests** rather than 9,753 of them. 391 digests are a list; 9,753 are a file of their own, and the roll-up binds the same claim — that the tests ran against these bytes — and is regenerated the same way. Its extension histogram (4,378 `.ymt`, 3,623 `.ymf`, 1,738 `.cut`, 6 `.ytyp`, 4 `.pso`, 4 `.ymap`) and its section census (9,753 `PSIN`/`PMAP`/`PSCH`, 9,745 `PSIG`, 8,978 `CHKS`, 3,047 `STRE`, 326 `STRF`, 12 `STRS`) were measured here and agree with `docs/metadata-encodings.md` exactly, which was measured by a separate probe |

`docs/corpus.md` and `docs/metadata-encodings.md` are cited above as the
independent readings these fixtures agree with. Both are working material a
clone does not carry — `README.md` says why — and nothing here needs them read:
what they corroborate is stated in the table.

Both manifests are located through **`RPF_METADATA`** rather than
`RPF_CORPUS`, because they describe payloads that are already out of their
archives; `README.md` says why that is a separate variable.

**`tools/metadata-dump` is what fills that directory**, and it is the step
rather than a note about it: it walks a corpus for `*.rpf`, descends every
nested archive, and writes out every `PSO`, `RBF` and resource `Meta` payload
it recognises. A dumped file's contents are exactly the payload. A dumped
resource `Meta` additionally carries **how many of its bytes are system
pages**, as a `sys` field in its file name — `00002_sys8192_…` — because a
`Meta` is a paged payload whose every pointer resolves against the boundary
between its system and its graphics pages, that boundary is the entry's rather
than the payload's, and `metadata::meta::parse` cannot be run without it.
`tools/metadata-dump/README.md` says why the name and not a sidecar.

**With `RPF_METADATA` unset the metadata tests are `#[ignore]`d and the harness
names each one; with it set and pointing somewhere else they fail.** That is not
the same rule as the one above, and the difference is deliberate: a skip has to
be reported rather than swallowed, and `eprintln!` is not a report, because
`cargo test` captures it. A
directory that was named and does not hold the corpus is a misconfiguration, and
the only outcome that says so is a failure. The `files` count in each manifest
is what a run is checked against, so a directory holding one payload cannot
satisfy a test whose claim is about 9,753 of them.

**No dictionary is tracked here, and none ever will be.** DR-006 and DR-047: a
name list derived from the game is not ours to redistribute, and after the
load-time `joaat(name) == key` check the dictionary is cosmetic rather than
load-bearing, so nothing in the suite needs one. The handful of names the
metadata tests use are inline in `crates/rpf-core/tests/metadata.rs` as
`NAMES_THAT_OCCUR` — eighteen measured to occur in the corpus, seven of them
against real `PSCH` structure and member hashes.

## Interoperation

On 2026-08-26 the sample was rebuilt by `rpf-core` — tight-packed, 65,160,704
bytes against the original's 144,504,832 — and the **reference implementation
read the result**: 3 archives, 25 leaf files, every checksum identical to the
row above. Neither implementation was written against the other's output.

That is the strongest evidence available without a game to load the archive.
It says the writer produces something a different reader understands. It does
not say the runtime will accept it. Only the game loading the archive would,
which is what `tools/acceptance/` stages.

Reproduce it with:

```
RPF_CORPUS=/path/to/corpus RPF_REQUIRE_CORPUS=1 RPF_REBUILD_OUT=/tmp/rebuilt.rpf \
    cargo test --test roundtrip
cd tools/oracle && cargo run --release -- /tmp rebuilt.rpf
```

That agreement is the reason this fixture is worth committing. A fixture can be
wrong in the same way its oracle is wrong (DR-005); two independent readings
agreeing is weaker than an in-game load, and much stronger than one reading.
